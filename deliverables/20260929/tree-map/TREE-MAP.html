WHAT THE PAGE SHOWS (T1, 29 Sep; T1b additions above)

One tree, read from the top down: the market → asset class or region → sector fund → the registry parent → cohort → names. Every tradable line on it (a fund or a name) carries a Geiger bar, and every cohort and heading carries the mean of the lines under it with an up/down count. There are two ways to look at the same tree:

  • OUTLINE — an indented list with a bar on every line. Loads without three.js, works at phone width (it is the default on a phone), and every cohort opens to its members.
  • 3D — the r3 market map with the cohorts hung under their registry parents. The upper tree is flat; a big cohort's rows step toward you. Desktop default. FLAT 2D shows it straight on.

The finder (top right) takes a ticker and answers with its path, market → … → cohort → name, and every fund that holds it with its weight. ?t=NVDA in the address does the same.

The 28 Sep market map (market-map-r3) is untouched: this is a new page beside it.

1 OCT · T4: THE CANVAS ON A RETINA SCREEN — LABELS AND NODES ON ONE PLANE

Alan opened the canvas on his Mac and the labels sat on a different plane from the balls and lines. The cause: on a scale-2 (Retina) screen the drawing buffer was made twice the CSS size, but the canvas element was never told its CSS size, so it took its buffer size as its CSS size — the picture spilled out of its box to the right and down while the labels, projected in CSS pixels, stayed where the box said. At scale 1 the two sizes are the same, so nothing showed.

Fixed: the canvas's CSS size is always the box's; the drawing buffer is CSS × the device scale (1, 1.5, 2, 3); the pixel ratio is set at start and again on every resize, and once a second if the window moves to a screen with another scale; every label is projected in CSS pixels from that same size. The same code draws the canvas, the whole-market 3D and a lifted area, so all three are covered. On open the canvas fits the whole tree in view. The hint line now reads "drag to pan · scroll to zoom · click an area to lift it into 3D" on the canvas and "drag to turn …" in the 3D.

WHAT COULD BE WRONG

  • Membership is from the 28 Sep lists, not from a table. The registry (step 1) carries no member lists, so the page uses the lists the registry was derived from, plus the 29 Sep admissions. If a name was moved on the board since 28 Sep, the tag shows it, the placement does not.
  • The "smallest cohort" home rule is mine, stated on the page. It puts NVDA in MEGACAP (9 names) rather than AI ACCELERATORS (16) or AI HARDWARE, because MEGACAP is the smallest of the three that claim it. Alan may prefer themes over MEGACAP; see decisions.
  • The live public.cohort_registry could not be read with the Hub's public key (permission denied: no SELECT grant to the anon role). The page uses data/cohort-registry-step1.json, which is the same 38 rows the migration inserted. Worth knowing: any Hub page that later reads the registry from the browser will hit the same wall until the grant is added.
  • The board read is a snapshot in tree.json (30 Sep 00:36 UTC, 613 rows, BLUE_CHIP 174 where the brief said 173). Rebuild with node scripts/build-tree-map.mjs to refresh it; the page does not read the board live.
  • Cohort means are unweighted (each name once). A fund's bar is weighted by holdings, so a cohort mean and its parent fund's blend are not the same thing; the card says so.
  • The fund cohorts (R8, the 49 automatic industry-fund cohorts) are not in the adopted registry and are not on the tree as cohorts; the industry funds are there with their holdings blend, as on r3.
  • The scout route answered tonight (as of 29 Sep); when it does not, the snapshot next to the page is used and the stamp says "page snapshot". BDXA has neither reading and says so.
  • Screenshots come from headless Chrome with the API's origin check relaxed for that throwaway browser only (as the r3 proof does); the page is unchanged.
