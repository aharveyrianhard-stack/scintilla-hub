Part B — the process, critiqued against public practice

B1 · One identity for a security — verdict: REPLACE (done on the branch)

How the public projects do it. LEAN (QuantConnect) keeps a map file per security: dated rows of "from this day this ticker string meant this security", so a rename or a dotted class never changes the identity the engine trades. zipline (Quantopian) keeps an asset database: every asset has a permanent sid, and ticker symbols are rows with ownership periods, so the same string can belong to two companies at different times and a lookup is always "as of a date". NautilusTrader addresses everything by an InstrumentId = symbol + venue ("BRK.B.NASDAQ"), so a symbol without its venue is not even a valid name. OpenFIGI (Bloomberg, open) gives a permanent id (FIGI) per share class that survives any ticker change, which is also what Q2a's REPLACE verdict asked for. The common thread: a service never spells a ticker; it asks a map, and the map is dated.

Our state on 5 Oct, morning. The settled-close robot asked Massive for "BRK-B"; the chart API carried { 'BRK-B': 'BRK.B' } as a frozen literal; the indicator contract carried a second copy of the same literal; the universe file the boot injected was a bare array (no map at all); the robot's database path had no map either; history-cut.mjs asked the reference endpoint for the canonical spelling. Three spellings, two frozen copies, one map-less file.

The single source, built. control/INSTRUMENT_MAP.json — one row per security: canonical (the Hub's spelling) · spellings per venue (massive: BRK.B, fmp: BRK-B, hub: BRK-B; MOG.A → massive MOG.A, fmp MOG-A) · FIGI and the provider's permanent id (null today: they live only on Fly; a job fills them, this file carries them) · valid_from / valid_to (the day the name entered the served set; 2026-08-20, 09-24, 09-27, 09-28) · tier (served / geiger-only). 590 rows, derived from the canonical universe by scripts/build-instrument-map.mjs, regenerated automatically by build-canonical-universe.mjs --write so an admission cannot leave it behind. ONE module reads it: services/identity/instrument-map.mjs (providerSymbol, canonicalSymbol, venueExceptions, buildUniverseFile, readUniverseFile). The two frozen copies now delegate to it.

The contract test that fails the build (tests/instrument-identity-contract.test.mjs, 11 tests): the map equals the builder's output byte for byte; the known spellings per venue and the reverse lookup; both old doorways answer from the map; no service, script or package carries a share-class spelling as a literal; a ticker inside a Massive request path must be under a name that says it is the provider's spelling (two reasoned baselines, like a ratcheted lint); every universe-file reader imports the module; the boots write the file through buildUniverseFile, never a bare array; the file refuses a bare array, a map-less object, a lie about its count or digest, and a spelling that disagrees with the map; a robot that must publish anyway reads a bare array as MARKED and floored from the whole map; without the map file the module falls back to the rule, marks it, and still spells BRK-B as BRK.B.

B2 · Contract tests between services — verdict: ADOPT (the first ones written)

Public practice. Pact: the consumer writes down the exact fields it reads; the producer's build verifies its real output against that statement, so a producer cannot drop a field a consumer depends on without its own build going red. Schema-first APIs (OpenAPI with Spectral, JSON Schema in CI) do the same with a schema file. Ours now: tests/contracts/payload-schemas.mjs states four contracts in a 40-line validator anyone can read — chart API → Geiger publisher (/candles), chart API → Hub board (/geiger, /quote), settled-close robot → chart API overlay (the artifact). tests/contracts-between-services.test.mjs checks each against a specimen recorded from the live producer today, against the real consumer code, and, for the settled-close robot, against the producer's own output. The candles contract names the BRK-B class at the boundary: provider_symbol must be the map's spelling, or the test says so by name.

B3 · A canary before a deploy, a smoke test after — verdict: ADOPT (scripted)

Public practice. Kubernetes readiness probes and Argo Rollouts analysis run the same checks against the new copy before traffic moves; a smoke test re-runs them after. The lanes already do the throw-away-machine pattern by hand, and by hand nobody curled BRK-B's daily chart on 2 Oct. Ours now: scripts/smoke-after-deploy.mjs — ten GET reads, one line each, exit 0/1: alive · ready and Geiger ready · the universe is the pinned one · a daily chart for the dotted ticker under the map's provider spelling · the other share-class name · previous close for a plain name · previous close for the dotted name · the Geiger is fresh and the dotted name is in it, not absent · an intraday rung has bars · metrics answer. The share-class names come from the map, not a literal. Live run 5 Oct 17:15 UTC: GREEN 10/10. --mode canary --base <throw-away machine> is the same script before a deploy. Its test proves every read fails by name on a stand-in (wrong spelling, named absence, old Geiger, moved pin, dead service).

B4 · "No new rule without its neighbours" — verdict: ADOPT (house rule proposed)

Public practice. Mature projects gate a behavioural rule four ways: a feature flag / kill switch so it can be turned off without a deploy (LaunchDarkly, Unleash; our SETTLED_HOLD_DISPUTED=0 already is one); an architecture decision record per rule — what, why, what it follows, what it touches, how to undo (Nygard's ADRs, adr.github.io); a test that names the neighbours (Rust's #[allow(…, reason)], ESLint's ratcheted --max-warnings, Argo's analysis against the canary); and a release gate that runs them together. The text proposed for BRIEF-20261002-AGENT-COMMON.md is in HOUSE-RULE-no-new-rule-without-its-neighbours.md and repeated at the end of this page. Today's branch follows it: the runbook lists the neighbours (G1's never-refuse boot, the 2 Oct blank-percentage incident, the pins, membership) and the tests exercise them together.

B5 · Observability — what Q2a/Q2b built vs the four golden signals; the one dashboard — verdict: CHANGE (proposal, not built)

Public practice. Google SRE's four golden signals: latency (how long an answer takes), traffic (how much is asked), errors (how often it fails, by cause), saturation (how full the machine is). For a data system Dagster adds a fifth, freshness (how old the newest row is). What we have: errors — covered (Q2a's cause-labelled counters on /metrics and /health, Q2b's heartbeat LATE/FAILING per job); freshness — covered well (the Geiger freshness block, geiger_ready, the previous-close state, the frame currentness); traffic — partly (request counters on the chart API, no per-route rate); latency — not measured (no p50/p95 per route; today's Lighthouse is a front-end proxy only); saturation — not measured (Fly CPU/memory, database connections, R2 rate). The one dashboard: Q2b's status page mock (deliverables/20261003/status/) extended with one row per service × the five signals, the ten smoke reads as its top strip (green/red with the line that failed), and "since when" on every red — the Hub itself never computes any of it; it reads /health, /metrics and the heartbeat table. Staged as a proposal; building it is a Hub lane after your yes.

The house rule, proposed text

For handoffs/BRIEF-20261002-AGENT-COMMON.md, replacing the one-line 3 Oct entry.

  1. Name its neighbours. Before adding or changing any guard, refusal, floor, retry, hold, schedule, backfill, spelling or format: list every rule that reads the same input, writes the same output or runs in the same window. Write them in the commit message and the runbook under "The neighbours".
  2. Test them together. One test file exercises the new rule WITH each neighbour. A rule tested alone is not tested.
  3. Prefer a maintained public pattern, cited, over an invention. Say which project does it this way. If none, say why ours must differ.
  4. A refusal is a mark, not a hold, unless Alan says otherwise. Publish what you have and NAME what you refused; the Hub shows the age and the names.
  5. Every rule has a switch and a record. An env var turns it off without a deploy; a short decision record (what, why, follows, neighbours, rollback) sits in the runbooks.
  6. A canary before, a smoke after. The smoke script GREEN on the throw-away machine before the deploy and GREEN on live after it; a RED line is the rollback reason.
  7. Contracts, not assumptions, between services. A field one service reads from another is stated in the contract schemas and checked on both sides. A spelling is never typed in a service: it comes from the identity module.
