What it is
A scheduled job, sentiment-news-10m, that calls the function sentiment-news every 10 minutes. A second job, sentiment-news-backfill, calls the same function every 5 minutes to work through the older headlines.
What it does
Reads the newest news headlines, scores each one against a word list (no AI model, no paid service), stores the words that fired, and rebuilds the per-stock daily mood rows. Those daily rows are what the Hub's SOCIAL → SENTIMENT tab and the NEWS page's mood read.
State
Running, and answering correctly since 15:40 UTC today. Since real answers began to be recorded (17:10 UTC) it has answered OK 26 times out of 26 finished runs; the back-filler 52 of 52. The watchdog shows it UP.

The exact error was read news -> 500, last seen today at 14:40:11 UTC. It happened on the run at 40 minutes past the hour, on and off, from 1 Oct 21:40 UTC to 5 Oct 14:40 UTC. Three faults sit behind it:
  1. It read the whole news table every run. It asks for "the newest 600 by publish time", and the table (594,917 rows) has no index for that order. On a quiet database that takes about 3 seconds. An hourly clean-up job ran at the same minute :40; together they passed the 8-second limit and the run failed. Moving the clean-up to :43 this afternoon (fix B) stopped the errors, but the slow read is still there.
  2. It never sees a headline that arrives late. Most headlines reach the table hours after their publish stamp. "Newest by publish time" looks only at the last three hours of stamps, so a late arrival is never scored: 5,754 of the last three days' 13,745.
  3. The back-filler stopped after its first slice. It asked for 1,500 headlines, the database hands out at most 1,000, and the job took "fewer than I asked for" to mean "finished". That was 24 Sep. It has answered "finished" 288 times a day since.
What breaks if stopped
The SENTIMENT tab's news line and the NEWS page's mood stop at today. Nothing else waits on it. Do not stop it.
A separate, older job (news-sentiment-10m, a one-number-per-stock roll-up) is healthy and still shown on the Hub for comparison; it is not part of this fault.
The fix
On branch hub/n1-sentiment-alerts-20261005, not deployed:
  • The 10-minute run takes the newest arrivals instead of the newest publish stamps. That uses an index that already exists (229 ms) and catches late headlines: on the live table at 21:28 UTC it found 365 unscored headlines where today's way found 49.
  • The back-filler is finished only when a read comes back empty, and can be told where to stop.
  • Days it has no time to rebuild in one run are kept on a waiting list instead of being dropped.
  • A failed read now reports the database's own message, so the cause is visible next time.
Staged for the coordinator, not applied: one new index (01), which ends the slow read for the function as it runs today, with no deploy.

What it is
A table, feed_alerts, and a scheduled job, feed-alerts-5m ("the old alert writer"). It is a different table from alert_log, the per-stock alerts behind the parked ALERTS room — that one holds 14,730 rows from 5–10 June, and no writer for it was found in the database.
What it does
Every 5 minutes it looks at ten feeds. If one reads RED it writes one line — "news feed DOWN — stale 14 min" — at most once per feed per half hour. That is all. It sends nothing to anyone.
State
The writer is still running: 288 runs in the last 24 hours, all successful, watchdog UP. It has written nothing for 17 days because none of its ten feeds has read RED since 18 Sep.

"Undelivered" means nothing was ever built to deliver them. Each row has a "delivered" box that starts as "no". No job, function or page ever changes it, and the "channel" box is empty on all 9,352. Nothing will ever deliver them.

One page reads the table: the Station's ALERTS panel shows the newest lines under FEED HEALTH, each tagged "undelivered", with a STALE badge.
What breaks if stopped
The Station's FEED HEALTH list could never show a new line. More important: the newer alarm system watches 13 feeds, and seven of the old writer's ten — news, fundamentals, analysts, events, economic, ribbon, crypto price — are not among them under those names. For those seven, this log is the only record that one went down.
The fix
Three options, all staged, none applied:
  • Mark the 9,352 as void (05) — recommended. The rows stay; the "delivered" box becomes blank and the channel reads "void — never sent". Fully reversible. It rewrites existing rows, so it waits for Alan.
  • Stop the writer (04) — not yet. First give those seven feeds a place in the newer alarm system; then switching this off loses nothing. Reversible in one line.
  • Delete the rows (06, a proposal only) — not recommended. It frees 1.3 MB and erases the June–September outage record.

What could be wrong · what was not done

  • The function was not run live. It was run offline against a stand-in database, and its new read was run against the live one. The first real run happens at deploy.
  • The function's own logs were not read. The command-line tool on this Mac has no log reader for functions; the error text comes from the receipt the function writes into the database, which keeps only the latest error. So "on and off since 1 Oct" rests on Q2b's count for 3 Oct (4 failures in 6 hours) and on the date the clean-up job was created, not on a full log.
  • The database's exact wording of the failure was not captured — the function recorded only "500". The cause is inferred from the measured 3-second full read and the 8-second limit. The fix makes the next failure say why.
  • Once late headlines are scored, earlier days' mood numbers will move as their missing headlines are added. That is the correction, but it is a visible change.
  • A long outage is not self-healing. The 10-minute run looks at the newest 600 arrivals, about 50 minutes' worth. If the job is off for longer than that, the gap is closed by the back-filler, not by the next run.
  • Linear SCI-63 was not opened — this session has no Linear connection. Its title and source were read from L1's local receipt and R1's report.
  • No pictures of a screen: nothing on a Hub or Station page changed.
