Scout tier · design

28 Sep 2026 · answer to "we need a more lightweight method" · working prototype: Scout · IWM · Fund valuation

The Hub gives every name the full treatment — live bars on seven timeframes, the Geiger, financials, estimates, the company view. That is why we carry 486 names and only 31 of IWM's ~1,970 stocks (3.3% of its weight). The suggestion: add a third, cheap tier underneath that screens every US stock every night from data we already receive in bulk, with no admission per ticker. You look at any list through it — IWM, a branch of the market map, a fund's holdings — and only the names you pick move up.

Promotion is your click, never automatic. The scout page gets a "promote" mark per row that writes the ticker onto the next admission sitting's candidate list (the same list the 27 Sep sitting used). Nothing drops down automatically either; a name leaves a tier only when you say so.

3 · Where the result lives — an R2 file, not a database table

Choice: one compressed JSON file per night in R2 (normalized/scout_v1/<date>.json.gz + latest.json.gz), served read-only by the chart API as /v1/scout?list=IWM.
Why: the scout is one whole-market snapshot that is always read whole (a page filters ~2,000–5,000 rows in the browser in milliseconds); no query ever needs one row. A file needs no migration, no new permission, no row-by-row writes, and old nights stay as dated files for free. The chart API already reads R2 for prices, so the Hub reaches it the same way it reaches everything else.
When a table would be better: if the Allocation tool needs to join scout numbers with saved picks in SQL. Then an additive public.scout_daily table is filled from the same file by the same edge-function pattern B1 uses for breadth. Not written, not applied — no database was touched.

One small permission to decide: the provider's R2 writer refuses every folder except FMP, Cboe (and, on the breadth branch, breadth). The scout needs normalized/scout_v1 added to that list — the same one-line change B1 made. It is not made on this branch; the prototype wrote nothing to R2.

6 · In plain words

What this page is. A proposal with a working prototype. The prototype ran once today on a temporary Fly machine that borrowed the batch app's keys and was removed afterwards. Its numbers are on the IWM page and the fund-valuation page.

What could be wrong. The scout is only as fresh as the last close; it is a screen, not a signal. FMP's holdings and trailing numbers can lag by days or a quarter. The RSI percentile uses about three years of history — enough to say "low for this stock lately", not "low for all time".

What was not done. No schedule installed, no chart API route deployed, no R2 or database write, no promote button (the page shows the design only). Those three steps wait for your go.
