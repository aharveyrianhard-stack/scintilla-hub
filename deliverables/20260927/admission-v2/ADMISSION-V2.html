2 · The tier

The smallest change that lets a name be computed but not shown: one list in the universe file (tiers.geiger_only, written by the builder) and one column on the Hub's table (public.tickers.role, 'full' or 'geiger_only'). No provider table changes: the audit found that the provider's own admission-flag migration (0020) cannot be applied by the writer login, and the provider does not need to treat these names differently anyway. Where each number comes from

  • Served set, frames, weekly depth, “not tracked”: the public chart API (/universe, /health, /candles), read today.
  • Row counts (364 active of 425 provider rows; 389 Hub rows, 364 active equities; 72 LIKED; 386 in composite_staged): read-only queries on the live database today.

  • Digests and scope ids: computed by the builder from the symbol lists.

What could be wrong

  • None of the 48 has been pulled or gap-reported. Any of them may be held; the builder then simply leaves it out.
  • Why daily fails for the 56 is not proven. The likely cause is the bar service's membership gate (the files the rollbacks removed); S2 recreates them and checks.
  • VXX was re-issued in 2018 and reverse-splits often; its stored series may be spliced.
  • The loader sources were copied from what is deployed (read this morning). If someone deploys a newer version first, the switch must be re-applied to it.
  • Without a canonical reader, the Station now trusts a self-consistent chart API list instead of a pinned one. The pages that bind the reader still compare name by name.

What I did not do

  • No push, no deploy, no database write, no Fly change, no provider pull. No paid model API.
  • I did not run the gap report, the history pull or the preflight: the provider key and storage credentials are not on this Mac, and I do not copy credentials.
  • I did not add a FUNDS tab to the Hub strip: the funds show on ALL and LIKED until Alan asks for one.
  • I did not touch the FMP indicator export (pinned to 365 in its own code) or the Geiger runner's code line.
